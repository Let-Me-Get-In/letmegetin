# Phase 10.1 Plan 01: Search pagination Summary

Search results now have a **total order** (distance, then place id) and are pageable with
`offset`, so hits past 100 are reachable without breaking the array response body. A caller
learns whether another page exists from `X-Has-More`, and the web search appends pages with a
"Voir plus" button.

## What changed

**Query stack.** `SqlAlchemyPlaceRepository.list_near` orders by `(distance, place.id)` and
takes a keyword-only `offset` applied after `.limit()`. The domain port documents the total
order so callers may page it. `search_places` now returns `SearchPage(hits, has_more)`, fetching
`limit + 1` rows and trimming — the repository stays a dumb `LIMIT/OFFSET` query and no
`COUNT(*)` runs against the 634k-row candidate set.

**API.** `GET /api/v1/places` gains
`offset: Annotated[int, Query(ge=0, le=10_000, description="Number of hits to skip")] = 0`,
injects `Response` to set `X-Has-More`, and keeps `response_model=list[PlaceSummaryOut]` with a
plain list return. The header is declared in the route's `responses=` because FastAPI does not
derive it from a `response.headers` assignment, so it appears in the published OpenAPI document.

**Contract.** `docs/openapi.json` regenerated (offset parameter, header, docstring); the export
is stable under a second run (identical sha1). `docs/public-api.md` documents the total ordering,
the pagination section (limit max 100, offset max 10 000, `X-Has-More`), the unchanged array body,
and the caveat that pages are only consistent while the data does not change.

**Web.** `placesPath(state, offset = 0)` sets `offset` only past page 1, so shared links keep
their URL shape; `toSearchParams` is untouched (paging is not shareable state).
`search-view.tsx` adds `PAGE_SIZE = 100`, `more`/`loadingMore` state and `loadMore`, which appends
the next page and turns the button off on a short page. The button is rendered only when `more`
and not `loading`.

## Deviations from Plan

**1. [Plan example, not a deviation of intent] Bulk fixture origin moved to (30.0, 4.0)**
- **Found during:** Task 1, before seeding.
- **Issue:** the plan suggested (44.0, 4.0) as an empty second origin; measured against the dev
  database, Avignon holds **47 real AccesLibre places** within 5 km, which would make the exact
  "100 rows then 50 rows" assertions fail locally.
- **Fix:** the 150 bulk rows cluster at (30.0, 4.0), which the same measurement showed holds
  **0** places near it and is ~1 850 km from `_ORIGIN`. No existing radius-scoped assertion is
  touched.

**2. [Rule 2 - missing critical functionality] `loadingMore` guard**
- **Found during:** Task 3.
- **Issue:** the plan's `loadMore` derived the offset from `places.length` with no in-flight
  guard, so a double click would append the same page twice.
- **Fix:** `loadingMore` state disables the button and short-circuits a re-entrant call.

No other deviations; the plan's design (offset over cursor, id tie-breaker, limit+1, array body)
was implemented as written.

## Threat notes

- T-10-08 (deep offset): mitigated by `le=10_000` and the existing `public_rate_limit`; no
  second query was added.
- T-10-09 (parameter types): `int` bounds enforced by FastAPI before the handler; a negative or
  non-integer offset never reaches SQL.
- T-10-11 (duplicate/skipped rows): mitigated by the total order and asserted by the new tests.
- No new network endpoint, dependency, or trust boundary was introduced, so no new threat flag.
