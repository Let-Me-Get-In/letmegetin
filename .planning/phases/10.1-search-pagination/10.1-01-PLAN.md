<objective>
Rank results by a total order and page beyond 100 hits without breaking the published contract
(SEARCH-03, ticket LET-34).

**What is wrong today.** `GET /api/v1/places` caps `limit` at 100 and has no `offset`, so hits
101+ are unreachable — the frontend hardcodes `limit: "100"` in `placesPath`. Ordering is
`.order_by(distance)` alone. `distance` is a float that is *equal* for every pair of places
sharing a coordinate, which the national AccesLibre import produces routinely (same building,
same address, several activities). Postgres is free to return tied rows in any order, and a
different plan, a parallel worker or a different `OFFSET` can order them differently. Once
paging exists, that is not cosmetic: a tie at a page boundary duplicates one row onto both
pages and drops another. Hence the requirement's wording — "a tie-breaker, not just distance".

**Design decisions, with the alternatives they beat.**

- *Tie-breaker = `place.id`.* Unique, immutable, already indexed as the primary key, and it
  makes the sort a total order for free. A "relevance score" was considered and rejected for
  this plan: the documented contract says "Distance-sorted search", the map-first UI depends on
  it, and `place.confidence` is only populated for dedup candidates (NULL for almost every
  imported row), so it would be a tie-breaker that ties. Ranking quality beyond distance is not
  part of SEARCH-03 and inventing a formula here would change result order for every existing
  consumer.
- *Pagination = `offset`.* The response body is a bare JSON array (`list[PlaceSummaryOut]`).
  Switching to an envelope (`{items, next_cursor, total}`) would be a breaking change for third
  parties on a live API. `offset` is an additive query parameter: old callers omit it and get
  page 1 exactly as before, new callers page. It is also correct here precisely because the
  ordering is now total.
- *`has_more` = limit+1, not `COUNT(*)`.* A count over the same predicate would double the cost
  of every public search at 634k rows, for a number no criterion asks for.
- *`offset` is capped.* Deep offsets re-sort the candidate set each time. `le=10_000` keeps
  100 pages of 100 available — far past the "beyond 100 hits" requirement — while bounding the
  work a single anonymous request can demand.

Output: total ordering, `offset`, `X-Has-More`, regenerated snapshot, docs, and a working
"show more" in the web search.
</objective>

Measured facts:
- `PlaceSummaryOut` already carries `distance` rounded to 0.1 m, so the ordering key and the
  displayed distance are not the same number; ordering must stay on the raw SQL value.
- The web BFF (`web/src/app/api/[...path]/route.ts`) forwards only `content-type` upstream, so
  `X-Has-More` does not reach the browser. The web therefore derives "more pages" from the page
  size, and `X-Has-More` is the signal for direct API consumers. Do not change the BFF in this
  plan.
- `_search` in the integration test builds params from `{"lat", "lng"}` plus overrides, so new
  query parameters are adopted by existing tests without edits.

Existing patterns to copy: `.limit(limit)` chaining in `list_near`; `Response` header setting is
not used in `api/v1/places.py` yet, so follow the `Response` injection style used elsewhere in
FastAPI rather than returning a bespoke object; `ReviewPageOut` in `api/schemas/places.py` shows
the repo's existing "page" shape, but note the place search deliberately does NOT adopt it
because it would break the array response.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous client → `GET /api/v1/places?offset=` | a caller controls how far into the result set the server sorts before returning |
| browser → web BFF → API | the page position is chosen client-side and forwarded verbatim |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-08 | Denial of service | deep `offset` re-sorting a large candidate set on a public endpoint | high | mitigate | `offset` is capped at 10 000 by `Query(le=10_000)` (422 beyond), page size stays capped at 100, and the endpoint keeps `public_rate_limit`, so the worst case per request is bounded and unchanged in shape from today's max-limit request. |
| T-10-09 | Tampering | `offset` / `limit` types | low | mitigate | Both are `int` with bounds enforced by FastAPI before the handler runs; a non-integer or negative value is a 422 and never reaches SQL. |
| T-10-10 | Information disclosure | `X-Has-More` reveals result-set size | low | accept | The signal is a single boolean, and the results themselves are public accessibility data; a caller can already infer size by paging. |
| T-10-11 | Information disclosure | duplicate or skipped rows at page boundaries | medium | mitigate | The order is made total by appending the primary key, so ties cannot reorder between requests; the integration test asserts disjoint, gap-free pages and identical repeated ordering. |
| T-10-SC | Tampering | package installs | high | mitigate | No new dependency in this plan; nothing to check against the package-legitimacy table. |
</threat_model>
