  <behavior>

    - rate 0.005, 0.01 and 0.25 → "sketch" (0 < rate ≤ 0.25)
    - rate 0.255, 0.26 and 0.50 → "partial" (0.25 < rate ≤ 0.50)
    - rate 0.505, 0.51 and 0.75 → "good" (0.50 < rate ≤ 0.75)
    - rate 0.755, 0.76, 0.99 and 0.995 → "very_good" (0.75 < rate < 1.0)
    - DOCUMENTATION_LEVELS is exactly ("none", "sketch", "partial", "good", "very_good", "complete") in order
    - for every (slug, min_pct, max_pct) in DOCUMENTATION_LADDER, documentation_level(min_pct/100) == slug and documentation_level(max_pct/100) == slug
    - get_place returns detail.documentation == Documentation.from_rate(detail.filled_rate)
  </behavior>
  <action>
    Create src/letmegetin/domain/places/documentation.py as a pure module (no SQLAlchemy, no
    FastAPI). Define DocumentationLevel = Literal["none","sketch","partial","good","very_good","complete"];
    DOCUMENTATION_LEVELS (the six slugs in order); DOCUMENTATION_LADDER (a tuple of
    (slug, min_pct, max_pct) DISPLAY bounds per D-01: none (0,0), sketch (1,25), partial
    (26,50), good (51,75), very_good (76,99), complete (100,100)); and a frozen Documentation
    dataclass with rate: float and level: DocumentationLevel plus a from_rate(rate) classmethod.
    The level is derived from the SAME rounded integer the UI prints (UI-SPEC rounding rule):
    percent = floor(rate * 100 + 0.5) — half-up, never Python's banker's round() — then
    documentation_level(percent: int) switches on the D-01 integer bounds: 0 -> "none";
    1..25 -> "sketch"; 26..50 -> "partial"; 51..75 -> "good"; 76..99 -> "very_good";
    100 -> "complete". Clamp percent to [0, 100] first. This is what stops "100 %" appearing
    beside a `very_good` level: rate 0.995 rounds to 100 and therefore `complete`.
    Do NOT keep a second, float-threshold ladder: one integer decides both the percent and the
    slug. DOCUMENTATION_LADDER's (min_pct, max_pct) pairs ARE those integer bounds, and the
    lockstep test asserts documentation_level(min) == documentation_level(max) == slug for each
    entry plus min-1/max+1 crossing into the neighbouring slug.

    Move the three completion helpers out of get_place.py into documentation.py as public
    functions — recorded(value: object) -> bool, leaf_slugs(nodes) -> list[str], and
    filled_rate(tree, values) -> float — and import them back in get_place.py (rename the
    private _recorded/_leaf_slugs/_filled_rate call sites). This is the single source so the
    search batched computation in 13-02 uses the identical denominator/numerator semantics and
    cannot drift (D-03). Do NOT change filled_rate's arithmetic.

    In get_place.py, add a documentation: Documentation | None = None field to PlaceDetail and
    set it to Documentation.from_rate(filled_rate) where filled_rate is computed.

    In api/schemas/places.py, add a DocumentationOut model:
    rate: float = Field(description="Share of the category-grid criteria with a recorded value, in [0.0, 1.0]") and
    level: str = Field(description="Documentation level slug: a stable enum in {none, sketch, partial, good, very_good, complete}, never display text (D-09)").
    Add documentation: DocumentationOut | None = Field(default=None, description="Documentation level derived from filled_rate") to PlaceSummaryOut; in
    PlaceDetailOut.from_detail set documentation=DocumentationOut(rate=..., level=...) from
    detail.documentation. Do not add the search flag here (that is 13-02); leave
    PlaceSummaryOut.documentation defaulting to None.

    Create tests/unit/domain/places/test_documentation.py covering the boundary cases in
    <behavior> (including the gap rates 0.005→1 sketch, 0.255→26 partial, 0.505→51 good,
    0.755→76 very_good, 0.995→100 complete), the six-slug order, the half-up rounding at exact
    .5 (0.005 → 1, not 0), and the DOCUMENTATION_LADDER ↔ documentation_level lockstep. Update tests/unit/application/places/test_place_detail.py
    to assert detail.documentation.level for the 0.5 case is "partial" (rate 0.5 → partial).
  </action>
