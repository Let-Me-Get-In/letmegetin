    - Add an "ODbL export" section stating: the export is a ZIP of places.csv / categories.csv /
      criteria.csv / answers.csv / aliases.csv / ATTRIBUTION.txt / manifest.json; `latest.json` points to
      the current snapshot and available deltas; the files are generated on the host by the operator
      (never per request) and served read-only; and the manifest's `schema_version` announces the shape.
    - In the same section document the DELTA CONTRACT explicitly (W-DELTA-CONTRACT): `latest.json.last_seq`
      stays at the snapshot boundary forever, so every delta is CUMULATIVE since that snapshot plus an
      overlap window (the `base`, `cumulative` and `overlap` fields in latest.json and the delta manifest
      say so); a partner must apply deltas in order over the snapshot, never treat a delta as a
      point-in-time diff.
    - In the same section document the CSV formula-injection guard RULE (F4): a leading `'` is prefixed
      only to the FREE-TEXT columns (places name/address_full/city/source_category; categories/criteria
      name) when the value starts with =, +, - or @; numeric/id/date/count/JSON columns (lat, lng, phone,
      postal_code, ids, dates, label, value) and the header row are NEVER guarded, so a negative longitude
      or +phone stays intact while a free-text formula is neutralised.
    - In the same section document what "origin id" means per file (I4, matching the 14-02 wording):
      places → the (source, source_id) pair; answers → the (place_id, criterion_slug) natural key
      (answers have no source-side surrogate id); categories and criteria → the slug. This is how EXP-01
      ("each row carrying a stable id and its origin id") is honestly satisfied.
