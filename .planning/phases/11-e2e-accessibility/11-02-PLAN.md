<objective>
Add an operator CLI command, `admin user ensure`, that idempotently creates an already email-verified
account for the e2e suite to log in through the real login form, and — for an existing account —
refuses to proceed silently if the supplied password does not match the stored one. This closes the
auth gate in front of the contribution and review journeys (E2E-01, ticket LET-35): today there is no
way to mint a verified account without an email round-trip, and `admin.py` has no `user` command at
all.

**Phase goal (ROADMAP):** "Prove the user journey in a browser and with assistive technology."

Purpose: the e2e repo must exercise authenticated writes, but `contribution-form.tsx` and
`review-form.tsx` gate writes on `email_verified`, and registration sends a verification email that a
headless suite cannot confirm. A minimal, idempotent operator command removes that friction without
opening a secret channel — the secret arrives by env var or a masked prompt, never on the command line.

Output: one application use case, one public validator in `register.py`, one Typer sub-command, unit +
integration tests, no new dependency.
</objective>

Add `src/letmegetin/application/accounts/users.py` with one async use case. Signature:
`ensure_user(users: UserRepository, email: str, password: str, display_name: str | None = None,
verified: bool = False) -> str`, returning a single human-readable outcome token the CLI prints:
`"created"`, `"verified"`, `"already verified"`, or `"unverified"`.

Follow the DDD layering exactly (the use case depends only on the port):

- Normalize `email` with `.strip().lower()`; validate with the **public**
  `is_valid_email(email)` imported from `application/accounts/register.py` and raise
  `DomainError("invalid email address")` on failure.
- Enforce `MIN_PASSWORD_LENGTH` exactly as `register` does (`DomainError` otherwise).
- Look up `users.get_by_email(normalized)`.
  - If none exists: construct `User(id=0, email=normalized, password_hash=hash_password(password),
    display_name=<stripped-or-None>, email_verified=verified)` and `await users.add(user)`, returning
    `"created"`.
  - If one exists: first `verify_password(password, existing.password_hash)`; on a mismatch raise
    `DomainError("password does not match the existing account")` — this is the loud, no-silent-skip
    guarantee, and it is the command's only write-free check. When it matches:
    - `verified and not existing.email_verified` → `await users.mark_email_verified(existing.id)` and
      return `"verified"`.
    - `existing.email_verified` → return `"already verified"`.
    - otherwise (unflagged, existing unverified) → return `"unverified"`.
- Never raise `EmailAlreadyUsed` here: an existing row is handled by the verify/match logic, not by
  the duplicate error.

Write `tests/unit/test_ensure_user.py` (pytest, `@pytest.mark.parametrize`, AAA, modules in
`test_<unit>_<scenario>` style) with an in-memory fake `UserRepository` implementing the port's
four methods over a `dict`. Cases: fresh email with `verified=True` → `"created"` with
`email_verified=True` and a hash `verify_password(password, hash)` accepts; fresh email with
`verified=False` → `"created"` with `email_verified=False`; existing unverified with `verified=True`
→ `"verified"` without a second insert; existing verified → `"already verified"`; existing with a
**wrong** password → `DomainError`; invalid email → `DomainError`; short password → `DomainError`.
Assert none of the return values or raised messages contain the password.
