<objective>
Make multiple `filters=` criterion ids narrow with AND instead of widen with OR (SEARCH-01,
ticket LET-34), and publish the corrected semantics on the public contract.

**Measured current behaviour — what the code does today.** In
`SqlAlchemyPlaceRepository.list_near`
(`src/letmegetin/infrastructure/persistence/repositories.py:725-734`) the criterion filter is a
*single* `EXISTS` subquery whose inner predicate is
`PlaceAccessibilityModel.criterion_id.in_(list(criterion_ids))`:

```python
statement = statement.where(
    select(PlaceAccessibilityModel.place_id)
    .where(
        PlaceAccessibilityModel.place_id == PlaceModel.id,
        PlaceAccessibilityModel.criterion_id.in_(list(criterion_ids)),
    )
    .exists()
)
```

`EXISTS(x IN (a, b))` is true when the place has a value for `a` **or** for `b`. So
`filters=a,b` is a union: adding a criterion returns *more* places, which is the opposite of
what a filter means and directly contradicts SEARCH-01. The inline comment
`# Existence is the MVP semantic` describes the value semantics (a value exists) but not the
combination, which is the defect.

**How this was verified, not assumed.** Three steps, against the running dev PostGIS
(`localhost:55433`, container `letmegetin-db`, migration head `0010`), each inside a transaction
that was rolled back (verified afterwards: `select count(*) from place where source='zz-proof'`
→ 0):

1. *Read the predicate.* The code above is the only place `criterion_ids` reaches SQL — a single
   `EXISTS` whose inner predicate is an `IN` list.
2. *Reproduce it in SQL.* Two criteria `c1`/`c2`, two places: `ZZ Both` holding both and
   `ZZ One` holding only `c1`. The production shape (`EXISTS ... criterion_id IN (c1, c2)`)
   returned 2 rows; one `EXISTS` per criterion, ANDed, returned 1 row (`ZZ Both`).
3. *Reproduce it through the real code path.* Calling the actual use case —
   `search_places(SqlAlchemyPlaceRepository(session), 45.5, 5.5, 500.0, criterion_ids=[c1, c2])`
   — returned `['ZZ Both', 'ZZ One']`, while the set of places genuinely holding both criteria
   is `['ZZ Both']`. `ZZ One` lacks `c2` and is returned anyway: the union is confirmed in the
   shipped code, not only in a hand-written query.

**Why no test caught it.** `tests/integration/test_places_search.py` has
`test_search_filters_on_criterion_ids` for a single id only. No test exercises two ids, so the
OR shape is untested. `web/src/lib/search.ts` does send multiple ids
(`params.set("filters", state.criteria.join(","))`), so real users hit this today: ticking a
second box in the UI broadens the result set.

Purpose: a filter that widens is worse than no filter — a wheelchair user who ticks "entrance
step-free" and "accessible toilet" gets every place matching either, presented as if both held.

Deliberately out of scope, recorded so the reviewer does not read it as an oversight: the
*value* semantics stay "a value exists for this criterion", whatever that value says. Whether
`entrance = no` should match a filter for "step-free entrance" is a product decision about
boolean and option criteria that SEARCH-01 does not ask for, and changing it here would rescale
the meaning of every filter in one commit. Keep it as a `shortcut:` comment on the predicate,
as the repo's convention requires.

Output: the ANDed predicate, a regression test that fails before and passes after, the contract
description, docs.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous client → `GET /api/v1/places?filters=` | a comma-separated id list from the public internet drives an unbounded number of SQL predicates |
| third-party consumer → documented contract | the endpoint is live on dev and prod; a silent semantic change breaks downstream assumptions |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-10-04 | Tampering | `filters` parsing → SQL predicate | medium | mitigate | Ids are parsed with `int()` in `_criterion_ids` (non-integers are a 422) and bind into per-criterion `EXISTS` predicates; no string ever reaches the SQL text. |
| T-10-05 | Denial of service | N correlated EXISTS subqueries from one request | medium | mitigate | Ids are de-duplicated before predicate construction, so a repeated list cannot amplify; each probe is a `place_accessibility_pkey` equality, and the endpoint stays behind `public_rate_limit`. |
| T-10-06 | Repudiation | silent semantic change for third parties | medium | mitigate | The AND change is documented in `docs/public-api.md` and in the `filters` description of `docs/openapi.json`, so the change is visible in the contract diff rather than only in behaviour. |
| T-10-07 | Information disclosure | filter combination reveals which accessibility values a place has | low | accept | This is the endpoint's purpose; the values are public accessibility data by design, and the rate limit bounds enumeration. |
| T-10-SC | Tampering | package installs | high | mitigate | No new dependency in this plan; nothing to check against the package-legitimacy table. |
