# Phase 8 Plan — Production Deployment & Operations

**Ticket:** LET-23 · **Requirements:** OPS-04, OPS-05, OPS-06
**Depends on:** Phase 7 stack (Postgres + Redis + API + web) merged.

## Task 1 — TLS, secrets and network hardening

**Files**
- `deploy/Caddyfile`: `app.{$DOMAIN}` → web:3000, `api.{$DOMAIN}` → api:8000; security headers,
  compression, request limits; `/metrics` is **not** routed.
- `deploy/.env.prod.example`: `DOMAIN`, `APP_DOMAIN`, `API_DOMAIN`, `POSTGRES_PASSWORD`,
  `REDIS_PASSWORD`, `LETMEGETIN_JWT_SECRET`, `SMTP_*`, `ALERT_WEBHOOK`, `SENTRY_DSN`,
  `NEXT_PUBLIC_SENTRY_DSN`, `GIT_SHA`.
- `docker-compose.prod.yml`: add `caddy` (80/443), drop the API/web host ports, add a private
  network, enable Redis `--requirepass`, pass `REDIS_PASSWORD` in the API URL, add healthchecks.
- `.gitignore`: `deploy/.env.prod`.

**Steps**
1. Caddy config with automatic TLS; for local smoke tests use `tls internal` when
   `DOMAIN=localhost` (documented, never in production).
2. Compose: only Caddy is published; API/web listen on the internal network.
3. Redis auth: `redis-server --requirepass …`; API `redis://:${REDIS_PASSWORD}@redis:6379/0`.
4. Document secret generation (`openssl rand -hex 32`).

**Verify:** `docker compose -p letmegetin-prod -f docker-compose.prod.yml config`; local HTTPS
smoke with `curl -k` on the app and API hosts; API/web host ports are closed.

## Task 2 — Backups and a tested restore

**Files**
- `scripts/backup.sh`: `pg_dump -Fc`, Redis `SAVE` + copy `dump.rdb`, timestamp dir, 7 daily /
  4 weekly rotation, non-zero exit on failure.
- `scripts/restore.sh`: restore into a scratch DB (`letmegetin_restore`), verify the table counts,
  then optionally promote; Redis restore path.
- `deploy/systemd/letmegetin-backup.service` + `.timer` (daily 02:00).
- `docs/runbook.md`: backup, restore, verification, promotion.

**Steps**
1. Run against the compose DB with the compose credentials.
2. The restore script **never** overwrites the live DB without `--promote`.
3. Print the row counts of `place`, `categories`, `review`, `users` after restore.
4. Test: create a marker row, backup, delete it, restore, assert it is back (manual/compose test).

**Verify:** backup then restore into scratch; counts match; a deleted marker is recovered.

## Task 3 — Metrics, error tracking and alerts

**Files**
- `src/letmegetin/core/metrics.py`: counters/histogram/gauge (request total by method/status,
  latency, 429, Redis up).
- `src/letmegetin/main.py`: middleware + `/metrics` (excluded from OpenAPI).
- `deploy/prometheus.yml`, `deploy/alerts.yml`, `deploy/alertmanager.yml`,
  `deploy/docker-compose.observability.yml` (profile `observability`).
- `src/letmegetin/core/observability.py`: Sentry init (if `SENTRY_DSN`) + `before_send` scrubber.
- `web/sentry.client.config.ts`, `sentry.server.config.ts`, `sentry.edge.config.ts`,
  `web/next.config.ts` (`withSentryConfig`, tunnel route).
- Tests: `/metrics` returns the counters; the endpoint is not in the Caddyfile; the scrubber
  removes emails/tokens; no DSN → no-op.

**Steps**
1. Middleware records every request; `/metrics` is unauthenticated but internal-only.
2. Redis gauge updated on a short interval (or at scrape via a custom collector).
3. Alerts: `ApiDown` (up == 0), `High5xxRate`, `High429Rate`, `RedisDown`; Alertmanager webhook
   from `ALERT_WEBHOOK`.
4. `promtool check rules deploy/alerts.yml` in CI.
5. **Sentry backend**: init only when `SENTRY_DSN` is set; `send_default_pii=False`,
   `traces_sample_rate=0.1`, release `GIT_SHA`; `before_send` strips `authorization`, `cookie`,
   request bodies and email-like strings.
6. **Sentry web**: `@sentry/nextjs` with `NEXT_PUBLIC_SENTRY_DSN`, tunnel route `/monitoring`,
   no session replay, no PII; build works with and without the DSN.
7. Sentry alerts: new issue + release regression; link in the runbook.

**Verify:** `/metrics` 200 with `letmegetin_http_requests_total`; Prometheus loads the target and
rules; `promtool` passes; `/monitoring` tunnel responds; Sentry is a no-op without a DSN.

## Task 4 — Retention, timers and runbook

**Files**
- `src/letmegetin/application/retention.py`: `purge(session, now) -> RetentionReport`.
- `src/letmegetin/admin.py`: `retention --dry-run`.
- `deploy/systemd/letmegetin-retention.service` + `.timer` (daily 03:00).
- Tests: unit cutoff logic, integration deletes only the old rows.
- `docs/runbook.md` and `docs/deploy.md` updated.

**Steps**
1. Delete `idempotency_key` older than 24h; refresh tokens expired or revoked older than 30 days.
2. `--dry-run` prints the counts without deleting.
3. Never delete contributions/reviews.
4. Document scheduling, manual run and rollback.

**Verify:** with two idempotency rows (old/new), the old one is deleted and the new one kept;
`--dry-run` changes nothing.

## Task 5 — Verification

1. Local TLS smoke: app and API over HTTPS, security headers present.
2. Backup → restore → marker recovered; scratch DB counts match.
3. `/metrics`, Prometheus rules and alerts load; `promtool` green.
4. Retention dry-run and real run verified.
5. CI: backend, web, OpenAPI, images, plus the new metrics/retention tests.

## Done when

1. The stack runs behind Caddy with TLS and production secrets; API/web ports are not public.
2. A restore test recovers data; backups rotate.
3. `/metrics` and the alert rules are live; Alertmanager has a webhook.
4. Retention runs on a timer and the runbook covers deploy/rollback/restore/incident.
5. Sentry captures API/web exceptions without PII; PostHog is explicitly deferred.
